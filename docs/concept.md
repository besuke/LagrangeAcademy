# LagrangeAcademy 構想（2026-11-07 初版）

## 0. この文書について

LagrangeAcademy は、LagrangeFinance を受け継ぐ金融計算の教材です。この文書は、何を目指すか、何を新しく加えるか、どう作るかを決めるための構想です。中身はまだ【設計案】で、決めたことと未決のことを分けて書きます（10 章が未決の一覧です）。

## 1. 目的と位置づけ

**目的**：金融計算を、次の 3 つを区別して学べるようにします。

- 結果が正しいと言える理由
- その理由がどこまで届くか
- どこから先が人の判断か

**中心の問い**：AI にできないことは何か。

この問いは「AI に任せても保証が残らないことは何か」と言い換えて扱います（2 章）。

**他のプロジェクトとの関係**：

| プロジェクト | 役割 | LagrangeAcademy との関係 |
|---|---|---|
| LagrangeFinance | 既存の教材（第 I〜III 部） | 内容を受け継ぐ。**LagrangeFinance 自体は変更しない** |
| RiemannFinMath（Riemann） | 計算ライブラリー（Rust と R） | 計算はここを使う。照合の結果（QuantLib との一致など）を教材の根拠にする |
| GaussQuant | QuantLib を使う R の計算 | 比較の相手。変更しない |
| LeanStudy | Lean 4 の学習 | Lean の書き方の土台。金融の命題は LagrangeAcademy の中に置く |

## 2. 中心の問い：AI にできないこと

「AI にできないこと」を能力の限界として列挙すると、すぐ古くなります。この教材では次のように捉えます。

> 結果に対する保証を、誰が、何によって与えているか。AI がその結果を出しても、保証が AI の外に残る部分はどこか。

この捉え方では、AI の性能が上がると境界は動きますが、問いの形は変わりません。

### 2.1 保証が AI の外に残る 5 つの領域

RiemannFinMath と LagrangeFinance の作業で実際に起きたことから整理します（【実例】は 2026 年 11 月の Riemann の作業記録による）。

1. **何を「正」とするかを決めること**（規範の選択）
   - 【実例】照合の正を QuantLib v1.42 とすること、日本式の債券計算を GaussQuant の規則に合わせること、二次情報の「市場慣行」を根拠に規則を変えないこと、2 月 29 日の応当日の扱い。これらはすべて人が決めた。AI は決まった基準に合わせる作業はほぼ完全にこなしたが、基準そのものは選んでいない。
2. **契約や条項の意味を確定すること**（解釈）
   - 【実例】ターゲット償還（TARN）の最終クーポンを「目標まで」にするか「全額」にするか。AI は一般的な形を【設計案】として選ぶしかなかった。曖昧さを解くには当事者の意図が要り、計算からは出てこない。
3. **世界を観測すること**（データと現実の接点）
   - 実際の気配、実際の休日、実際の取引規約は、渡されて初めて扱える。【実例】カレンダーは QuantLib とは全日付で一致したが、「実際の市場休日」としての正しさは未検証のまま残っている。市場の気配値を表に出さないという制約も、この境界の一部である。
4. **何を検査すべきかに気づくこと**（問いの立て方）
   - 【実例】PRDC の差分感応度で、金利ボラティリティを 0 まで動かすと乱数の対応が崩れる誤りがあった。テストはすべて通っており、幅とパス数を変える実験の表の異常（判定が変わる経路が 54%）で初めて見つかった。AI はテストを通せるが、テストの網から漏れるものは、別の角度の問いがないと見つからない。
5. **責任を負うこと**（説明と署名）
   - 数値に署名し、誤りの説明を引き受ける主体にはなれない。
   - 【実例】作業環境のアプリ制御が実行ファイルを止めたとき、またはウェブサイトが自動取得を拒んだとき、AI は回避せずに人に判断を返した。境界を越えてよいかを決めるのは、責任を持つ側である。
   - 【実例】別のスレッド宛ての指示を、AI はそのまま実行してしまった。文面の外にある「意図した宛先」は AI には見えない。

### 2.2 Lean が境界をどう動かすか

Lean の証明は機械が検査します。そのため、**証明を書いたのが AI でも、正しさは書き手への信頼に頼りません**。これによって「AI にできないこと」は、次の 2 つに絞られます。

- **何を命題として書くか**（仕様）：どの性質を証明すべきかを選ぶこと。命題が意図とずれていれば、証明は正しくても役に立たない。
- **どの仮定を受け入れるか**（公理とモデル）：対数正規の FX、Hull–White の金利、完備市場。仮定は置くものであり、その妥当性は証明の外にある。

この教材は、AI が証明を書ける時代に、人が担う部分を「仕様を書くこと」と「仮定を引き受けること」として教えます。

## 3. 保証の階段

各章のすべての結果に、次の 4 段のどれで保証されているかを付けます。

| 段 | 保証の種類 | 何が保証するか | 例 | AI の役割 | 残るもの |
|---|---|---|---|---|---|
| 1. 証明 | 機械検査された真 | Lean の型検査 | クーポンの分解、プット・コール・パリティ、無裁定の上下限 | 証明を書く | 命題が意図どおりか |
| 2. 照合 | 独立した実装との一致 | 外部の実装 | QuantLib と全件一致（FX スマイルの 1176 点など） | ほぼ自動化できる | 外部の実装が正しいか、条件が同じか |
| 3. 統計的検証 | 誤差の範囲での一致 | 標本と誤差の評価 | モンテカルロが標準誤差の 4 倍以内 | 自動化できる | 偶然の一致、誤差評価の前提 |
| 4. 仮定・設計 | 人の判断 | 判断した人 | モデルの選択、条項の解釈、照合の正 | 選択肢と根拠を出す | 判断そのもの |

Riemann の文書が使っている区分は、この階段にそのまま対応します。

- 【ソース確認】は段 2 の前提（何と照合したか）
- 【実行照合済み】は段 2
- 【設計案】は段 4
- 「未確認の推定」は、どの段にも届いていないこと

### 3.1 証明の段の中の 3 つの信頼水準

段 1（証明）の中も一様ではありません。ユーザーが共有した『Lean Programming for AI Agents』第 1〜2 章の解説（2026-11-07）は、証明の信頼を 3 つの水準に分けています。

1. **カーネルが検査した証明項**：Lean のカーネルが、形式的な命題の成立を検査した。
2. **命題の一致**：証明した命題が、本当に証明したかったことと一致している。
3. **外部の結果を仮定として明示**：外部のツールや AI の結果を公理として受け入れるなら、その公理を明示している。

水準 1 は機械が判定します。水準 2 は、2.2 節の「何を命題として書くか」そのもので、人が確かめます。この教材では、外部の結果を公理として置くこと（水準 3）は原則として行いません。必要なら、その公理と理由を章に明記します。

なお、この区分は解説から取ったもので、原書そのものは読んでいません（未確認）。

**定義上の等式と、仮定から導く定理**：同じ解説（第 2 章）は、Lean が次の 2 つを区別することを強調しています。

- 計算すれば一致する定義上の等式（`rfl` で閉じる）
- 推論で示す命題としての等式（帰納法や既存の定理が要る）

金融数学では、これは次の区別に対応します。

- 定義からそのまま出る恒等式：クーポンの分解、ペイオフの恒等式
- モデルの仮定を使って初めて成り立つ定理：無裁定の上下限、二項モデルのリスク中立確率

各命題に、どちらかを書きます。

### 3.2 証明の段の合格条件

AI が証明を書く前提で、次の場合は合格としません。

- `sorry` で証明を省略している。
- `axiom` で根拠のない前提を加えている。
- `partial` で停止性の保証を外している。
- 本来の命題を弱い命題にすり替えている。たとえば `True`、または仮定を強めすぎた命題（`theorem patch_ok : True := trivial` は何も示さない）。

**機械で確かめること**：

- `lake build` が警告なしで通る。
- `#print axioms` で、各定理が `propext`、`Classical.choice`、`Quot.sound` 以外の公理に依存しない（`lean/scripts/print_axioms.lean`）。

**人が確かめること**：命題が、対応する Rust の実装と条項に合っていること。合っているかを確かめた人と日付を章に書きます。

**階段に上がらないもの**：浮動小数点の丸め、乱数、市場データの再現。これらは段 1 に上がりません。たとえば Black の式の実数としての性質は証明できますが、浮動小数点で計算した値の誤差は照合か誤差評価で扱います。この線引き自体を教えます。

## 4. Lean で証明する命題の候補

Lean 4 と Mathlib の実数で書けるものから選びます。数値の計算ではなく、**計算が拠り所にしている恒等式・不等式・構造**を証明します。

| LagrangeFinance の章 | 命題の候補 | 難しさ |
|---|---|---|
| II-1 キャッシュフロー | 割引係数が正なら、正のキャッシュフローの現在価値は正。利回りについて価格は単調に減る（正のフロー） | 易 |
| II-2 金利カーブ | フォワードが非負なら割引係数は満期について非増加。ブートストラップした割引係数がパーレートを再現する（1 期間ずつの代数） | 易〜中 |
| II-3 OIS | 日次複利の積の分解（期間の分割について複利は積になる） | 易 |
| II-4 オプション | ペイオフの恒等式 `max(S−K,0) − max(K−S,0) = S − K` と価格の線形性からのパリティ。コール価格は行使価格について単調で凸（バタフライ）。二項モデルの無裁定 ⇔ `d < 1+r < u` ⇔ リスク中立確率が (0,1) にある | 易〜中 |
| II-4 アメリカン | 早期行使できる権利の価値は、ヨーロピアンの価値以上（後ろ向き帰納の各段で max を取るため） | 中 |
| II-5 CDS | 生存確率は非増加で [0,1] にある（ハザードが非負なら） | 易 |
| II-8 コール債 | 発行体コールつきの債券の価値は、コールなしの価値以下 | 中 |
| II-9 PRDC | `a > 0`、`f ≤ c` のとき、`clamp(a S − b, f, c) = f + a[(S − K₁)⁺ − (S − K₂)⁺]`（`K₁ = (b+f)/a`、`K₂ = (b+c)/a`）。Riemann の静的複製の拠り所 | 易 |
| II-9 ターゲット償還 | 「目標まで」の条項では、どの経路でも支払ったクーポンの累計が目標を超えない（有限列の帰納） | 中 |
| 第 I 部・日付 | 営業日への調整を 2 回しても 1 回と同じ（冪等性） | 中（カレンダーの表現しだい） |

最初の 1 つは、PRDC のクーポンの分解を勧めます。理由は次の 3 つです。

- 純粋に実数の代数で、Mathlib の基本だけで書ける。
- Riemann の実装（静的複製）の正しさに直接つながる。
- 「証明は正しいが、命題が契約の条項と一致しているかは人が確かめる」という 2.2 節の要点を、そのまま示せる。

2026-11-07 にユーザーが決めた章立てです。章番号は Quarto が自動で付け（`number-sections: true`）、序章とはじめには番号なしにします。

| 序章 | 保証の階段と、AI にできないこと | 2〜3 章の内容。PRDC のクーポンで、Rust・Lean・R の分担を通しで示す |

| 6 | 無裁定 | 支配の原理、プット・コール・パリティ、二項モデルの無裁定、コールスプレッドの上下限 |

## 6. 各章の書式

各章に次の欄を必ず置きます。

1. **計算**：何を計算するか。RiemannFinMath の関数、または R のコード。
2. **保証**：結果ごとに階段の段（証明・照合・統計的検証・仮定）と、その根拠。根拠は照合した相手と版、誤差、実行日。
3. **Lean**：その章の命題。命題がどの計算を支えるか、何を支えないか。
4. **人が決めたこと**：照合の正、規約、モデル、条項の解釈。誰がいつ決めたか。
5. **AI に任せたこと**：実装、照合、証明の作成など。AI の出力をどう検査したか。

5 の欄は、「AI にできないこと」を抽象論ではなく、毎章の具体的な記録として積み上げるためのものです。

## 7. 作り方（技術）

**役割の分担**（2026-11-07 に決定）：Rust で書き、Lean で証明し、R で描画する。

| 層 | 道具 | 役割 | 保証の段 |
|---|---|---|---|
| 実装 | Rust（RiemannFinMath） | 計算 | 照合（QuantLib など）、統計的検証 |
| 証明 | Lean 4 と Mathlib | 計算が拠り所にする恒等式・不等式 | 証明 |
| 描画 | R と Quarto | 表と図、本文 | Rust の結果をそのまま示す。R で計算し直さない |

Lean の命題と Rust の実装は、自動ではつながりません。ユーザーが共有した解説が紹介している AWS Cedar（Lean で仕様、Rust で実装）の例のように、「実装が仕様を満たすか」は別に確かめる必要があります。この教材では、次の 2 つでこの間を埋めます。

- 命題の左辺を、実装の式と同じ形で書く。例：`min (max (a S - b) f) c` は、Rust の `(a S - b).max(floor).min(cap)` と同じ形。
- 実装の数値は照合（段 2）で確かめる。

**QMD の役割**（2026-11-08 に決定）：

- Rust と Lean のソースコードを教材として示すのは、第1章（Rust）と第3〜5章（Lean）だけである。
- それ以外の金融計算は、ビルド・インストール済みの R パッケージ RiemannFinMath を使う。各章の QMD は `R/utility_LAD.R` を読み込み、そこを共通の入口として RiemannFinMath の公開関数を呼ぶ。
- 描画時に Rust をビルドしない。価格式を R で書き直さない。R は入力の準備、関数の呼び出し、結果の表・図への整形だけを行う。

- **文書**：Quarto の book。LagrangeFinance と同じ形式で、HTML と PDF を出力する。
- **計算**：RiemannFinMath（R から呼ぶ）。LagrangeFinance の GaussQuant による計算は比較の相手として残す。
- **Lean**：`lean/` に Lake のプロジェクトを置いた（2026-11-07）。Lean 4.35.0 と Mathlib v4.35.0（Mathlib のリリースのタグ）で、Lean のモジュール方式（`module`）を使う。Mathlib はビルド済みのファイルを `lake exe cache get` で取得する。
- **検査**：Quarto の描画とは別に、3.2 節の合格条件を証明の段の成立条件とする。

## 8. 守ること

- LagrangeFinance・GaussQuant・Riemann の既存の内容は、この教材のために変更しない（必要な変更は各プロジェクトの作業として行う）。
- 市場の気配値（Bloomberg のデータ）は表や出力に出さない。
- 確かめていないことを断定しない。保証の段を付けられない記述は、「未確認」と明記する。
- 「AI にできないこと」の実例は、実際の作業記録に基づくものだけを書く。推測で作らない。
